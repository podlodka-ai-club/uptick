# Следующая итерация: устойчивость решения и доступ к наблюдениям

После серии из шести SRE-прогонов исправлены два механизма, мешавших
проверке памяти. Новых запусков SRE в этой итерации нет; старые sealed-планы
и результаты не менялись. Изменения не доказывают экономическую пользу памяти.

## Восстановление решения после таймаута

В registry добавлена необязательная `TimeoutRecoveryPolicy`. В CLI `run` и
`benchmark` она включается флагом `--recover-decision-timeouts`: максимум две
попытки по 45 секунд, общий deadline 120 секунд, включая закрытие клиента и
получение замены. В startup spec сохраняется выбранная политика. По умолчанию
поведение прежнее; pinned `evaluate-v2` не принимает этот override.

Повторяется тот же structured request до исполнения действия. Старый клиент
закрывается перед созданием нового. Ошибки схемы, авторизации и внешняя отмена
не повторяются. Ответ после истечения deadline отвергается. Это кооперативные
asyncio deadlines: они не могут принудительно остановить зависший синхронный
код или провайдер, бесконечно подавляющий отмену. Финальный `aclose` остаётся
обязанностью владельца клиента.

Телеметрия результата и `last_telemetry` учитывают все попытки; при неполных
данных расход остаётся неизвестным. Подробности доступны через `last_attempts`
обёртки. Значения 45/120 — начальная политика, её эффект на живых прогонах
ещё не измерен.

## Полное наблюдение за пределами короткого контекста

При подключённом observation handoff runner добавляет `exact_read_record_id`
к обрезанной записи истории после сохранения канонического перехода и выдачи
разрешённой закладки. Ссылка не выдаёт новое право доступа: существующий reader
проверяет run, namespace, iteration и происхождение записи. При отключённом
handoff новая возможность не появляется.

Бюджеты отдельной записи и сериализованного списка сохраняются. Повторное
действие заменяет старое наблюдение; устаревшую ссылку прикрепить нельзя.
Точное чтение учитывается в бюджете действий, но не вызывает действие среды
и не порождает фиктивный переход опыта.

Интеграционный тест прячет нужное поле за длинным префиксом, обновляет последнее
наблюдение, затем читает исходную запись по ссылке и использует полученное поле
в следующем действии. Это проверка транспорта и бюджета с тестовой моделью,
а не доказательство, что настоящая LLM всегда выберет чтение.

## Проверка

Полный suite после интеграции: **984 passed, 2 skipped**. Ruff по изменённым
production-файлам и тестам прошёл. Отдельный runner-тест подтверждает две
попытки LLM при одном исполненном действии среды.

## Локальная проверка уроков и следующий эксперимент

В `artifacts/memory-next-decision-preparation-01/strict-incident-collection-02/`
собрано 12 реальных переходов и 8 outcomes локальной ControlledIncidentEnvironment.
Сборщик перебирал публичные действия в фиксированном порядке, без обращения
к правильному ответу. Существующие extraction/validation/persistence механизмы
получили **4 активных урока**, которые доступны после повторной композиции
runtime из SQLite. Условия уроков заданы конфигурацией экспериментатора;
автоматическое открытие схемы условий этим не проверяется.

Идентичность среды для валидации связывает исходник и закрытую конфигурацию
fixture; её digest и служебные declarations не попадают в provider messages.
Это возможно для локальной среды, но не снимает ограничение identity SRE API.

Правильные парные запросы лежат в `paired-requests-02/requests/` внутри этой
коллекции. Использованы реальные стартовые наблюдения четырёх evaluation cases,
поиск по публичному коду инцидента, одинаковые лимиты контекста, одно решение
и одно действие. Эпизодическая ветка получила 2/2/3/3 эпизода, ветка уроков —
по одному релевантному уроку. Предыдущие requests с нерелевантным episodic
результатом для seed 101 исключены до вызовов модели. Коллекция 01 с хэшем
только публичного интерфейса также исключена: такой хэш не фиксировал мир.

Исполняемая копия восьми запросов и план зафиксированы в
`artifacts/memory-next-decision-execution-01/frozen-pair-02/`.
Это **development-сравнение одного сконструированного семейства**, не новая
независимая held-out выборка и не SRE-результат. Старые shadow-подсказки не
используются как активное знание.

После отдельного согласия пользователя выполнены **8 решений Terra medium**
через подписку Codex, максимум два параллельно. Авторитетный результат:
`artifacts/memory-next-decision-execution-01/frozen-pair-04/readout.json`;
проверка неизменности запросов и счётчиков — `verification.json` рядом.

| Ветка | Восстановления | Учтённые токены | Байты пользовательского контекста, сумма |
| --- | --- | --- | --- |
| Эпизоды | 4/4 | 65 606 | 24 196 |
| Валидированные уроки | 4/4 | 62 232 | 12 556 |

Действия совпали во всех четырёх парах. Уроки сохранили результат с **−5,14%**
учтённых токенов и **−48,11%** байтов контекста. Это измеренная экономия объёма
на этих четырёх development cases, не доказанное улучшение качества решений.
Учёт всех восьми provider requests полный, повторов нет. Денежная стоимость
не сообщается; cached tokens различаются (13 056 против 26 112), поэтому
пересчитывать эту разницу в деньги или делать вывод о скорости нельзя.

Две предшествующие попытки не отправили запросы модели: `frozen-pair-02`
остановилась при создании клиента из-за API-key конфигурации процесса,
`frozen-pair-03` — на неподдерживаемом параметре `max_output_tokens=1200`
(все request_count=0). Для успешной попытки API-key переменные исключены
только из дочернего процесса без чтения значений; `max_output_tokens` убран
одинаково из обеих веток. Тексты одобренных пользователем сообщений,
наблюдения, память и схема решений не изменились. Новых SRE-прогонов нет.
